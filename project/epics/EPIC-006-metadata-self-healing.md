## Objective

"313.events should require as little manual event maintenance as possible." No event should enter the human follow-up queue until all applicable automated repair strategies have been attempted. This epic makes event metadata (venue address/city, description, ticket/event link, image, category) repair itself automatically wherever a repair can be made with real, already-known, or already-fetched data — and only ever asks a human when no automated strategy applies.

## Why it matters

Recurring, avoidable manual cleanup was the direct trigger: `migration_027_followup_dismissed.sql`'s own header quotes the Product Owner — "I have run all of the sql's and I am still getting empty fields in the admin panel - how can we make this more seamless and auto-healing?" The 2026-09-21 discovery pass (repository/database read-only audit, no code changed) confirmed concrete, repeated, source-specific gaps: Outer Limits Lounge events missing only `description`; Trinosophes events missing `description`, venue address/city, and ticket/event link on every row (100%, not source-dependent, since `cron-trinosophes.js` never writes those fields at all); Redford Theatre missing `description` and ticket/event link on every row for the same structural reason; Metro Times' own fetched pages reliably carry `og:street-address`/`og:locality`/`og:region`/`og:latitude`/`og:longitude` in their header comment, none of which `cron-metrotimes.js` extracts — a concrete "already have the data, throwing it away" gap. Meanwhile a self-growing curated+learned venue→address/city resolver already exists and ships today (`api/admin-venues.js`), just wired only into the Press-coverage "create event" form, not into any automatic repair path.

## Repair priority (locked, governs WP ordering)

A. Canonical data 313.events already owns (venue_id → venues table). **SH.1.**
B. Metadata already present in upstream responses/pages but currently discarded. **SH.4** (Metro Times `og:*` fields), **SH.3** (event-specific link repair — source-provided first, then recovered from source HTML).
C. Trusted cross-source enrichment (a later phase of SH.3, and any future cross-source description backfill).
D. Constrained generated metadata (**SH.2**, descriptions) — requires provenance (**SH.6**) first, since a generated value is the lowest-authority tier and must never be able to silently outrank or hide a manual correction.
E. Human intervention — the Needs Follow-up queue, evolved by **SH.7** into an exception-management queue that only ever surfaces what automated repair could not resolve.

**Do not implement generated descriptions before deterministic source enrichment (A/B/C) is in place.** This is a direct, binding reordering from the discovery-review approval, not a suggestion.

## SH.4 implementation note (2026-09-21)

Implemented per the Product Owner's explicit SH.4 scope/constraints, pulled directly (not via the general discovery-review flow SH.1 went through). Extracts `og:street-address`/`og:locality` in `parseEventPage()` from the same fetched HTML already in hand (no new request), using the existing generic `getMeta()` helper plus a new `metaOrNull()` wrapper that treats an empty/whitespace `content=""` attribute as absent rather than a blank real value.

The one design decision worth flagging: this connector's upsert is a full-column `merge-duplicates` write, so any column present in the payload is written unconditionally on every run — unlike SH.1's ingestion-time integration in `cron-feeds.js`, which had never previously sent `venue_address_raw`/`venue_city_raw` at all and so had no pre-existing-value hazard to guard against. Metro Times *does* have that hazard (it upserts the same event rows repeatedly), so satisfying "preserve an existing nonblank value" required extending the connector's pre-existing status-preserving lookup (originally added to stop status being clobbered) to also fetch `venue_address_raw`/`venue_city_raw`, and computing the final value per row through the full four-tier precedence before it ever reaches the upsert payload — one extra `select` field on an existing request, not a new network call.

`parseEventPage` is now exposed on `module.exports` for direct unit testing (`module.exports.parseEventPage = parseEventPage;`), mirroring the existing `cron-dossin.js` precedent for `parseDossinEvents`. 12 new tests in `test/cron-metrotimes-sh4.test.js`; full 16-file regression suite passes together. **2026-09-21: pushed to `origin/main`** (confirmed via `git fetch` + `git rev-list --left-right --count origin/main...main` = `0 0`); status moved to `REVIEW`. Production execution/impact verification (did the deployed connector actually extract and write these fields on a real run) remains pending — same constraint as every other WP 0.5/SH production-verification gap in this repo right now.

**WP 0.7 evidence note:** implementing SH.4's "preserve an existing nonblank value" requirement surfaced a concrete, general instance of the exact hazard WP 0.7 (`EPIC-001-ingestion-platform-scaling/phase-0-stabilize-instrument.md`) already names: `cron-metrotimes.js`'s upsert is a full-column `merge-duplicates` write, so **any** column it sends is written unconditionally, overwriting a reviewer's manual correction to that column on the very next run, not just the previously-known `category` case WP 0.8 already tracks. ## SH.N implementation note (2026-09-21)

Pulled directly after a Product-Owner-requested comparison of four candidate next work packages: SH.N (this one), Ticketmaster venue/location enrichment, remaining deterministic source-metadata recovery (Trinosophes/Redford Theatre and similar), and generated descriptions (SH.2). SH.N was recommended and approved because it was the only one of the four fully independent of the production-access blocker recorded in `DEBT-002` (read-only presentation logic, no database write of any kind), lower-risk than any DB-writing candidate, and it directly targets the architectural gap SH.1's own BEFORE-measurement note already flagged: SH.1's raw-column copy is a compatibility/self-healing mechanism, not the permanent way public pages should resolve a linked venue's canonical data. (Ticketmaster enrichment's own next step turned out to require reading current production rows to tell "Ticketmaster genuinely has no address" apart from "needs entity resolution" — itself blocked by `DEBT-002`; Trinosophes/Redford Theatre's description and ticket-link gaps turned out not to be recoverable from source at all on inspection; generated descriptions are explicitly out of sequence per this epic's own locked priority ordering, gated behind SH.6.)

**Architecture chosen: per-query PostgREST embedding (option B), not an `events_public` view revision (option A).** `events.venue_id references venues(id)` is a real foreign key, so every consuming query adds `venues(name,address,city,lat,lng)` to its own `select=` parameter — PostgREST resolves the embed automatically. This requires no schema/view migration, no manual SQL-Editor step, and no new `schema_migrations` row: it is a pure code change, deployable through the exact same `git push` path already used for SH.1/SH.4. `events_public` (migration_025, extended by 029 and 034) was deliberately left untouched: it is consumed only by `index.html` today, its existing `coalesce(v.name, e.venue_name_raw)` / `coalesce(v.city, e.venue_city_raw)` already satisfies the locked NAME/CITY precedence rule exactly, `index.html` never renders a street address at all (confirmed by reading the file — nothing to add there), and — the deciding factor — modifying the view would require a new manually-applied production migration at a time this session already confirmed migration application is blocked (`DEBT-002`), stacking onto at least one earlier view-altering migration (`migration_034_clothing_optional.sql`) whose production-applied state can't currently be confirmed either. Choosing a mechanism that needs zero database changes was a direct, deliberate response to that risk, not a default.

The shared precedence rule itself, `resolveVenueDisplay(row)`, is a small, fully self-contained pure function (no DOM, no network — verified by directly `eval()`-extracting and testing the real shipped source, not a reimplementation). This project has no build step and no shared client-side module mechanism — every page already duplicates its own small helpers (`radar.html`'s own header comment states this explicitly, and `map.html`'s pre-existing header comment independently confirms the same convention for its Places/coordinate logic) — so rather than introduce a new shared-file pattern inconsistent with that established convention, the function is duplicated verbatim across every consuming browser page, with a Node-side twin (`resolvePublicVenueDisplay`) added to `api/_lib/venue-lookup.js` (the existing shared home for venue pure functions) for the one server-side consumer. The "single source of truth" the Product Owner asked to prefer is the data relationship and precedence *rule* — resolved the same way, through the same real foreign key, everywhere — not a single physical file, which this codebase's own architecture doesn't support without adding a bundler (out of scope for this WP).

**Surfaces normalized, including two found during the required audit beyond the four named:** `calendar.html`, `map.html`, `event-template.html` (the three the Product Owner named that query raw `events` directly), plus `radar.html` (editorial-article cards showing a matched event's venue/city — found by grepping the repo for every `venue_name_raw`/`venue_city_raw`/`/rest/v1/events` consumer) and `api/event-meta.js` (server-rendered social-preview `<title>`/`og:description` tags — same audit). `index.html` needed no change (see above). Files confirmed out of scope by the same audit: `venue-template.html`/`venues.html`/`api/venue-meta.js` (venue-page surfaces reading canonical `venues` data directly, no raw event fields involved), `api/sitemap.js` (ids/timestamps only, no venue text), `api/submit.js` (an intake form, not a display of an already-resolved event), and `admin.html`/`api/admin-events.js`/`api/admin-editorial.js`/`api/admin-venues.js` (explicitly out of scope per the assignment; confirmed untouched and unaffected — Needs Follow-up's `getMissingFields()` logic and its raw-column query were not read or modified).

**Map behavior (`map.html`, and `calendar.html`'s own embedded map tab, which duplicates the identical `VENUE_LATLNG_MAP`/`resolvePlace()` pattern):** both pages previously resolved event pins through a separate, fragile client-side name-matching join against the whole `venues` table (`loadVenueLatLng()`) — venue_id was not used for coordinates at all. Per the explicit "a canonical venue with lat/lng may provide canonical coordinates where the existing architecture already supports that relationship" allowance, `resolvePlace()` now checks a canonical, venue_id-resolved coordinate (carried through from the same `venues(...)` embed) first — the real FK, never fabricated, never geocoded. Critically, this was implemented as a strictly **additive** preferred path: the original `VENUE_LATLNG_MAP`/`loadVenueLatLng()` name-matching fallback was left completely intact and still runs exactly as before whenever no canonical coordinate is available, so no event that got a precise pin today loses it — only events that can now resolve more reliably through the real foreign key (rather than by fragile name text-matching) gain one. No geocoding was added; unresolvable events still fall back to a city/suburb centroid exactly as before, never a fabricated pin.

**Architectural check answer (required by the assignment): YES.** If SH.1's production repair had never run at all, an event with a valid `venue_id` and a real canonical venue address now displays that address correctly on every applicable public surface — proven directly in `test/sh-n-venue-display.test.js`'s dedicated "architectural check" test, which feeds `resolveVenueDisplay()`/`resolvePublicVenueDisplay()` an event with every raw field `null` and a complete canonical venue, and asserts the canonical name/address/city/coordinates are returned. SH.1's raw-column copy is no longer load-bearing for public display wherever `venue_id` resolves — it now matters only as the fallback for events that are `venue_id`-unlinked or whose canonical venue itself has a gap, exactly the role the Product Owner specified.

**No production data was mutated.** No `UPDATE` was run against `events` or `venues`, SH.1's production repair was not run, no venue was created, no fuzzy matching or geocoding was added, no ingestion connector, event status, follow-up state, description, category, event link, or image field was touched.

**Testing:** `test/sh-n-venue-display.test.js` (new) extracts `resolveVenueDisplay()`'s real source out of all four HTML files via regex and `eval()`, asserting byte-for-byte identity across all four copies (the "keep every copy in sync" contract each file's own comment states), then runs the full 7-scenario acceptance-criteria precedence matrix plus the architectural-check scenario against both the browser copy and the Node twin (`resolvePublicVenueDisplay`), asserting the two independently-implemented copies agree on every case — real browser/Node behavioral parity, not just textual sameness. It also does structural/wiring checks per surface (each query embeds `venue_id`+`venues(...)`, each mapping function actually calls the resolver, the legacy map name-matching fallback is verifiably still present and checked *after* the new canonical path, admin files remain untouched, and unrelated event fields are unchanged). No DOM is exercised (`decodeEntities()` needs a real `document`, unavailable in plain Node, and this project has no `jsdom` dependency to add one) — full-page rendering was instead verified by direct code review against every acceptance-criteria example. Full 17-file regression suite (the 16 pre-existing files plus this one) passes together.
