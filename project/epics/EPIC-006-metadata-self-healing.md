## Objective

"313.events should require as little manual event maintenance as possible." No event should enter the human follow-up queue until all applicable automated repair strategies have been attempted. This epic makes event metadata (venue address/city, description, ticket/event link, image, category) repair itself automatically wherever a repair can be made with real, already-known, or already-fetched data — and only ever asks a human when no automated strategy applies.

## Why it matters

Recurring, avoidable manual cleanup was the direct trigger: `migration_027_followup_dismissed.sql`'s own header quotes the Product Owner — "I have run all of the sql's and I am still getting empty fields in the admin panel - how can we make this more seamless and auto-healing?" The 2026-09-21 discovery pass (repository/database read-only audit, no code changed) confirmed concrete, repeated, source-specific gaps: Outer Limits Lounge events missing only `description`; Trinosophes events missing `description`, venue address/city, and ticket/event link on every row (100%, not source-dependent, since `cron-trinosophes.js` never writes those fields at all); Redford Theatre missing `description` and ticket/event link on every row for the same structural reason; Metro Times' own fetched pages reliably carry `og:street-address`/`og:locality`/`og:region`/`og:latitude`/`og:longitude` in their header comment, none of which `cron-metrotimes.js` extracts — a concrete "already have the data, throwing it away" gap. Meanwhile a self-growing curated+learned venue→address/city resolver already exists and ships today (`api/admin-venues.js`), just wired only into the Press-coverage "create event" form, not into any automatic repair path.

## Repair priority (locked, governs WP ordering)

A. Canonical data 313.events already owns (venue_id → venues table). **SH.1.**
B. Metadata already present in upstream responses/pages but currently discarded. **SH.4** (Metro Times `og:*` fields), **SH.3** (event-specific link repair — source-provided first, then recovered from source HTML).
C. Trusted cross-source enrichment (a later phase of SH.3, and any future cross-source description backfill).
D. Constrained generated metadata (**SH.2**, descriptions) — requires provenance (**SH.6**) first, since a generated value is the lowest-authority tier and must never be able to silently outrank or hide a manual correction.
E. Human intervention — the Needs Follow-up queue, evolved by **SH.7** into an exception-management queue that only ever surfaces what automated repair could not resolve.

**Do not implement generated descriptions before deterministic source enrichment (A/B/C) is in place.** This is a direct, binding reordering from the discovery-review approval, not a suggestion.

## SH.1 implementation note (2026-09-21)

Implemented per the Product Owner's "APPROVED WITH REFINEMENTS" review: extended `api/_lib/venue-lookup.js` (the existing exact-match, no-fuzzy venue_id resolver) rather than creating a new module, per the explicit instruction to reuse the smallest appropriate existing venue-resolution functionality. `resolveVenueAddressCityRepair` is a pure function (no network) implementing the three-tier authority order; `buildVenueDetailsMap`/`buildLearnedVenueAddressCityMap` supply its canonical/learned data, both fail-soft to empty Maps on any error. One deliberate addition beyond the letter of the review: both map builders detect same-normalized-name collisions (two canonical venues, or two conflicting historical addresses, sharing one name) and treat them as unresolved rather than picking one — a direct application of the review's own "no fuzzy matching" / "never guess" principle to a real schema edge case (`venues_name_city_key` is unique on `(lower(name), lower(city))`, so duplicate names across cities are legal). Flagged here for visibility since it wasn't spelled out verbatim in the review.

Dual demonstration: `api/cron-feeds.js` (ingestion time — this connector already resolved `venue_id` per row but never populated address/city) and `scripts/sh1-repair-existing-venue-address-city.js` (existing events — a manually-invoked script, explicitly not the future SH.5 scheduled process; conditional PATCHes re-guard every field as still-null at write time to close the read-then-write race). 41 test cases across three new files (`test/venue-address-repair.test.js`, `test/cron-feeds-venue-repair.test.js`, `test/sh1-repair-existing-events.test.js`) plus the full pre-existing 12-file WP 0.5 suite all pass together. No production database access was available this session; production before/after measurement (refinement 10) remains pending — see the WP 0.5 production-verification gap this epic inherits the same constraint from. **2026-09-21 Product Owner review:** architecture and safety behavior accepted as implemented (canonical-authority order, exact-match-only, fail-closed on ambiguity, additive-only, both demonstrations, no scheduled cron introduced, no unrelated parser behavior changed). ## SH.4 implementation note (2026-09-21)

Implemented per the Product Owner's explicit SH.4 scope/constraints, pulled directly (not via the general discovery-review flow SH.1 went through). Extracts `og:street-address`/`og:locality` in `parseEventPage()` from the same fetched HTML already in hand (no new request), using the existing generic `getMeta()` helper plus a new `metaOrNull()` wrapper that treats an empty/whitespace `content=""` attribute as absent rather than a blank real value.

The one design decision worth flagging: this connector's upsert is a full-column `merge-duplicates` write, so any column present in the payload is written unconditionally on every run — unlike SH.1's ingestion-time integration in `cron-feeds.js`, which had never previously sent `venue_address_raw`/`venue_city_raw` at all and so had no pre-existing-value hazard to guard against. Metro Times *does* have that hazard (it upserts the same event rows repeatedly), so satisfying "preserve an existing nonblank value" required extending the connector's pre-existing status-preserving lookup (originally added to stop status being clobbered) to also fetch `venue_address_raw`/`venue_city_raw`, and computing the final value per row through the full four-tier precedence before it ever reaches the upsert payload — one extra `select` field on an existing request, not a new network call.

`parseEventPage` is now exposed on `module.exports` for direct unit testing (`module.exports.parseEventPage = parseEventPage;`), mirroring the existing `cron-dossin.js` precedent for `parseDossinEvents`. 12 new tests in `test/cron-metrotimes-sh4.test.js`; full 16-file regression suite passes together. **2026-09-21: pushed to `origin/main`** (confirmed via `git fetch` + `git rev-list --left-right --count origin/main...main` = `0 0`); status moved to `REVIEW`. Production execution/impact verification (did the deployed connector actually extract and write these fields on a real run) remains pending — same constraint as every other WP 0.5/SH production-verification gap in this repo right now.

**WP 0.7 evidence note:** implementing SH.4's "preserve an existing nonblank value" requirement surfaced a concrete, general instance of the exact hazard WP 0.7 (`EPIC-001-ingestion-platform-scaling/phase-0-stabilize-instrument.md`) already names: `cron-metrotimes.js`'s upsert is a full-column `merge-duplicates` write, so **any** column it sends is written unconditionally, overwriting a reviewer's manual correction to that column on the very next run, not just the previously-known `category` case WP 0.8 already tracks. This is recorded here as evidence for WP 0.7's existing scope, cross-referenced from that WP's own notes. **WP 0.7's scope is not expanded and no fix beyond SH.4's own two fields (`venue_address_raw`/`venue_city_raw`) is implemented as part of this entry.**
