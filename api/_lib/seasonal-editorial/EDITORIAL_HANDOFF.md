# Seasonal collections: editorial handoff

PRIVATE. This folder (`api/_lib/seasonal-editorial/`) is not routable and not a static path. Nothing in it is served to the
public; the only public seasonal data is `seasonal/published-entries.js`, which is generated and today holds no entries.

Engineering has built the gate; editorial supplies the evidence. Nothing here was verified, licensed or approved by
engineering. A destination becomes a public card only when its record passes **all five** gate items below, and the
tests fail if a record's declared `status` disagrees with what its fields prove.

## Workflow

Official verification -> Image rights -> Image file or linked image -> Publication approval -> Live destination card

| Ledger state | Meaning | What the record has |
|---|---|---|
| `HOLD_UNVERIFIED` | Not public. | no `evidence` item at level `official`, and/or no confirmed `relevance` |
| `CONTENT_VERIFIED` | Official source read, relevance confirmed. Image work not started. | gate items 1 + 2 |
| `IMAGE_PENDING` | Verified; an image source or license is recorded but the asset or its rights are incomplete. | 1 + 2, partial 3 / 4 |
| `READY_FOR_REVIEW` | Content, image and rights complete; waiting for a person to approve. | 1 - 4 |
| `PUBLISHED` | Public card. | 1 - 5 (including `approval`) |

`status` is the field on each entry; `readiness(entry)` in `seasonal/collections.js` derives the state from the fields, and
`status` must equal it. The ledger rows in `candidates.json` carry the same state (regenerated by `scripts/build-halloween-qa.js`).

## When one destination completes review

1. **`entries.json`**: edit that destination's record (keep `id` stable; it links the ledger, the photo library and the
   saved QA choices).
   - Gate 1, official verification: an `evidence` item `{ level: "official", note, url (https, the official page),
     websiteChecked: true, checkedAt: "YYYY-MM-DD", checkedBy }`.
   - Gate 2, relevance: `relevance: { confirmed: true, note, checkedAt, checkedBy }`.
   - Gates 3 and 4, the image, by ONE of these routes (the gate reports which one in `gate.imageRoute` / `rightsRoute`):
     - **Third-party license** (Creative Commons or similar): `image.acquired { file, bytes, sha256, width, height,
       acquiredAt }` with `image.src === acquired.file`, plus `image.license`, `image.licenseUrl` (a real https URL
       from the license; never invented), `image.credit`, `image.rightsVerifiedAt`.
     - **Owner-authorized photo** (the owner's own archive): build the record from the photo library with
       `ownerPhotoImage(photoId, opts)` in `editorial.js`. It computes `bytes`, `sha256` and pixel size from the real file and copies the
       authorization wording verbatim. It records `ownerPhoto { photoId, reviewRef, authorization { statement, grantee,
       recordedBy, recordedAt }, verifiedAt, verifiedBy }`. Owner authorization is **not** a Creative Commons license: it carries no
       license URL and `validateAssets` rejects one. The original photo identifiers (file name, Apple Photos id) stay in
       `photo-library.json` and are looked up by `photoId`; the build checks they exist and match. The route fills items 3
       and 4 only. It never approves a destination or publication.
     - **Labelled illustration** (owner strategy 2026-10-11, temporary): build the image block with `illustrationImage(src, opts)` in
       `editorial.js`. It computes `bytes`, `sha256` and size from the card file and records `image.illustration { statement,
       suppliedBy, recordedBy, recordedAt }`. The record must carry NO `image.remote` and NO `image.ownerPhoto`. The public
       renderer always shows the "Illustrative image" badge. It fills items 3 and 4 only, is never documentary photography of the
       destination, and never approves a destination. Replace it with an authentic or licensed photograph when one exists; only the
       record's `image` block changes, not its verified facts.
     - **Linked image** (owner decision 2026-10-11): `image.remote { src, sourcePage, credit, acceptedBy, acceptedAt,
       riskNote }`, with `image.src` the local generated card as the fallback. The owner's recorded acceptance of the
       copyright risk is **not** confirmed usage rights; no rights-holder permission is on file for any linked image.
   - Gate 5, approval: `approval: { by, at: "YYYY-MM-DD" }`. Added only by the person approving. Nothing in this repository writes it.
   - `status`: set to the state the fields now prove (it is checked).
2. `node scripts/build-halloween-qa.js` (ledger and QA data), `node scripts/build-publication-review.js` (migration review),
   `node scripts/build-seasonal.js` (published projection and pages). All three have `--check` modes the tests run.
3. If the file is new, commit it under `assets/seasonal/` (never overwrite the shared card artwork).
4. Run `node test/run-all.js`.

Only a record that is declared and derived `PUBLISHED` is copied into `seasonal/published-entries.js`, and only in display form (`publicEntry` in `editorial.js`: id, name, city, region, categories, featured, summary, website, image source fields). Evidence, reviewer, rights/authorization, hashes, parked images and approval stay private. Publishing needs
no edit to `index.html`, `data/dont-miss.json`, the renderer, the CSS or the rewrites.

## Launch preview: `/fall?qa=1&launch=1`, `/fall-color?qa=1&launch=1`

On a Preview, the QA bar has a **Launch preview** button when a collection has proposed records (`launch-1.json`). It draws only the
proposed records with the public card (the page's hero, filters and card layout are unchanged), the Don't-miss rail from the
`featured` records, and one QA line per card: "PROPOSED, not approved", the gate state and the image route. Nothing in it is
published or approved. A record that is not `READY_FOR_REVIEW` with no approval cannot be in `launch-1.json` (the QA build fails).

## Reviewing images: `/halloween?qa=1`

QA mode lists all 52 Halloween destinations with their gate state, outstanding requirements, and every image option.
It exists only on Previews and local development: `/api/seasonal-qa` answers 404 unless `VERCEL_ENV` is exactly `preview`
or `development` (and 404 if `APP_ENV` is `production`), and the client also refuses the production host names. Previews
are behind Vercel SSO. `?review=1` and `?fixtures=1` no longer exist.

- Choices a reviewer makes are saved in that browser (`localStorage` key `313-halloween-qa-image-choices-v1`,
  `{ destinationId: optionId }`) and exported as JSON. **Option ids are stable** (`gen-halloween-N`, `link-<destinationId>`,
  `313p-xxxxxxxx`): they are what saved choices point to. Never rename or reuse one. `test/fixtures/halloween-qa-7e094df.json`
  freezes the ids as of the consolidation and a test fails if one disappears or a default moves.
- **Defaults are pinned** in `defaults.json` (44 generated card, 5 linked official image, 3 owner photo, as on `feature/halloween-completion`).
  A newly added option is selectable but is never a default; changing a default is an explicit edit to that file.
- Each option shows its source, credit, rights status, image kind (photo, promotional artwork, generated artwork), and, for
  linked images, whether permission is on file (never, today), the owner's recorded risk acceptance, and the load test
  (Chrome, 2026-10-11, size returned). Promotional artwork (logos, title graphics, illustrations) is kept distinct from
  photography and never counts as depicting the destination. Real images that were found and not chosen are listed
  under each record as `recorded_alternatives` (not selectable).

## Image fallback chain

linked image (if any) -> generated card (`image.src`) -> alternate generated cards (`image.alternates`) -> branded
placeholder (`/assets/placeholders/event-800.webp`) -> CSS placeholder block. Implemented by `seasonal/image-fallback.js`:
a failed URL is remembered for the page session and skipped, there are no retries or loops, and no broken-image icon is
ever shown. When a linked image falls back, its credit line is hidden and the "Illustrative image" badge appears.

## Linked images (owner decision, 2026-10-11)

Jody accepted the legal risk of linking third-party and official-site images with credit and a generated-card fallback. No
rights-holder permission is on file for any linked image. If an owner objects, delete that image's row in
`linked-images.json` (and `image.remote` on any record using it); the card returns to the generated image.
`linked-images.json` holds 21 rows (12 from the supplied catalogue, 9 official-site images read on 2026-10-11), each with
the load test result, image kind, source type, risk acceptance, `permission_on_file: false`, and the unchosen alternatives.

## Where the editorial spreadsheets map

`313events_ALL_252_image_links.csv` and `313events_destination_image_manifest_2026.csv` columns:
`photographer_credit` -> `image.credit`; `license_permission` -> `image.license` (+ `image.licenseUrl`);
`image_source_page` -> `image.sourcePage`; `image_filename`/`asset_key` -> the file under `assets/seasonal/`;
`image_status` of `LICENSE_VERIFIED_DOWNLOAD_PENDING` = IMAGE_PENDING at best, and only if the destination is also
`CONTENT_VERIFIED`. Neither file records official-source verification, which is gate 1 and is separate.

## Guards that must not be weakened

- `scripts/scope-guard.js` (CI): compares HEAD with `origin/main`, allows protected files only by exact path, and fails
  when the base is missing, shares no history, or the diff is empty. To approve another protected file, add its exact
  path to `ALLOWED` in a reviewed change; do not loosen the check.
- No unpublished destination name, image candidate URL, rights note or evidence text may appear in any served file
  (`test/seasonal-qa-route.test.js`). The public `seasonal/` folder holds six files only.
- A declared status that disagrees with the gate fails the tests; an owner photo or linked image never satisfies approval.
